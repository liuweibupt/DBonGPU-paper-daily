SYCLDB: A Cross-Vendor Heterogeneous Analytical DBMS

arXiv 提交 2026-11-23 cs.DB cs.DC 主题相关度 0.706

Ivan Donchev Kabadzhov, Eugenio Marinelli, Raja Appuswamy

中文摘要

AI 与分析型工作负载的快速增长，推动了对快速、交互式分析数据处理的需求。这也促使越来越多的研究关注如何设计加速型分析数据库引擎，利用现代 GPU 扩大计算规模。GPU 能够提供现代分析所需的大规模数据并行能力，但软件生态仍以 CUDA 等闭源且绑定特定厂商的编程模型为主，限制了软件在不同厂商 GPU 之间的可移植性。本文提出 SYCLDB，一个基于 SYCL 开放标准的端到端分析数据库引擎，旨在通过一套代码在多种加速器上实现高效、与具体硬件无关的执行。SYCLDB 将核心关系算子实现为模块化的 SYCL 内核，将这些内核与基于 Apache Calcite 和 Apache Thrift 的 SQL 前端集成，并支持通过 Apache Arrow 高效导入列式数据。借助这些设计，同一套 SYCL 代码可以在 Intel、AMD 和 NVIDIA GPU 上执行分析查询流水线，从而降低对特定厂商 GPU 编程栈的依赖。

查看英文原文摘要

The rapid growth of AI and analytical workloads has increased the need for fast, interactive analytical data processing. This, in turn, has led to a surge of interest in designing accelerated analytical database engines that can exploit modern GPUs to scale computation. While GPUs provide the massive data-parallelism required by modern analytics, the software landscape remains dominated by closed-source, vendor-locked programming models, like CUDA, limiting portability across multi-vendor GPUs. In this work, we present SYCLDB, an end-to-end analytical database engine built upon the SYCL open standard, designed to enable efficient, hardware-agnostic execution across a wide range of accelerators using a single codebase. By implementing core relational operators as modular SYCL kernels, integrating them with a SQL frontend based on Apache Calcite and Apache Thrift, and supporting Apache Arrow for efficient columnar ingestion, SYCLDB reduces dependence on vendor-specific GPU programming stacks by enabling a single SYCL codebase to execute analytical query pipelines across Intel, AMD, and NVIDIA GPUs.

核心结论
SYCLDB 使用同一套 SYCL 代码在 Intel、AMD 和 NVIDIA GPU 上执行分析查询流水线，降低了对特定厂商 GPU 编程栈的依赖。
创新点
1. 基于 SYCL 开放标准构建端到端分析数据库引擎，以模块化 SYCL 内核实现核心关系算子，支持跨厂商 GPU 执行；2. 将算子内核与基于 Apache Calcite 和 Apache Thrift 的 SQL 前端集成，并通过 Apache Arrow 支持高效的列式数据导入。

Estimating GPU Roofline Arithmetic Intensity with Off-the-Shelf LLMs and Compiler Artifacts

arXiv 提交 2026-11-24 cs.DC cs.PF 主题相关度 0.549

Gregory Bolet, Giorgis Georgakoudis, Konstantinos Parasyris, Harshitha Menon 等 7 人

中文摘要

GPU 开发者使用性能剖析来了解计算和数据移动行为，但获取目标硬件可能会延误优化工作。本文研究现成的大语言模型（LLM）能否在不执行目标 GPU 工作负载的情况下，估算 Roofline 模型中的算术强度，即浮点运算次数（FLOP 数）与设备内存传输字节数之比。我们评估了 3 个模型（deepseek-v4-flash、gemini-3.7-flash 和 gpt-5.6-sol），共测试 179 种组合，涵盖 5 类内核、来自 NVIDIA 和 AMD 的 4 款 GPU、4 种并行运行时（CUDA、HIP、OpenMP 和 OpenCL）以及修改后的代码变体，并比较了仅提供源代码的查询、附带编译器产物的查询和在沙箱中运行的智能体分析。提供编译器产物后，落在实测值的 1/1.20 至 1.20 倍之间的算术强度估计所占比例由 8%–14% 提高至 26%–32%，据此判断工作负载受带宽限制还是受计算限制，在 78%–92% 的运行中正确。使用编译器产物时，FLOP 数估计在 59%–88% 的运行中满足 1.20 倍的误差容限，设备内存流量估计的达标比例为 36%–40%。对于 gpt-5.6-sol，智能体分析将满足同一 1.20 倍误差容限的算术强度估计比例提高了 6.5 个百分点，但其成本中位数和延迟中位数分别达到编译器辅助查询的 3.6 倍和 2.5 倍。其他模型的成本同样升高，改善在统计上并不明确。这些发现表明，在目标 GPU 难以获取时，LLM 估计有望帮助确定优化优先级，而受缓存行为影响的设备内存流量是精确预测算术强度的主要障碍。

查看英文原文摘要

GPU developers use profiling to understand computation and data movement, but access to target hardware can delay optimization. We investigate whether off-the-shelf large language models (LLMs) can estimate Roofline arithmetic intensity (the ratio of floating-point operations (FLOPs) to device-memory bytes) without executing the target GPU workload. We evaluate three models (deepseek-v4-flash, gemini-3.7-flash, and gpt-5.6-sol) across 179 combinations of five kernel families, four NVIDIA and AMD GPUs, four parallel runtimes (CUDA, HIP, OpenMP, and OpenCL), and modified code variants, comparing source-only queries, queries with compiler artifacts, and sandboxed agentic analysis. Compiler artifacts raise the share of arithmetic-intensity estimates within a factor of 1.20 of profiled values from 8-14% to 26-32%, while the resulting bandwidth-bound or compute-bound classifications are correct in 78-92% of runs. With compiler artifacts, FLOP estimates meet the 1.20x tolerance in 59-88% of runs, compared with 36-40% for device-memory traffic. Agentic analysis increases the share of arithmetic-intensity estimates within the 1.20x tolerance by 6.5 percentage points for gpt-5.6-sol, at 3.6x the median cost and 2.5x the median latency of compiler-assisted queries; the other models incur higher costs without a statistically clear improvement. These findings suggest LLM estimates could help prioritize optimization when GPU access is constrained, while identifying cache-dependent device-memory traffic as the main obstacle to precise arithmetic-intensity prediction.

核心结论
与仅提供源代码相比，加入编译器产物使算术强度估计落在性能剖析实测值 1.20 倍误差容限内的比例由 8%–14% 提高到 26%–32%，带宽受限或计算受限的判定在 78%–92% 的运行中正确。目标 GPU 难以获取时，这类估计有望帮助确定优化优先级，但缓存相关的设备内存流量仍是精确预测的主要障碍。
创新点
1. 评估现成 LLM 在不运行目标 GPU 工作负载的条件下估算 Roofline 算术强度的能力，在覆盖多类内核、GPU、运行时及代码变体的组合上，对比仅源代码查询、编译器产物辅助查询与沙箱中的智能体分析；2. 分别检验 FLOP 数和设备内存流量的估计精度，并评估算术强度估计用于瓶颈分类的正确率。

X-BQSR: Holistic Acceleration of Base Quality Recalibration for Scalable Genomic Analysis

arXiv 提交 2026-11-23 cs.DC 主题相关度 0.545

Eugenio Marinelli, Ivan Donchev Kabadzhov, Raja Appuswamy

中文摘要

随着测序成本持续下降，基于基因组学的精准医学日益重要。基因组分析工具包（Genome Analysis Toolkit，GATK）是从原始基因组数据中识别可用于指导临床决策的变异的标准框架。碱基质量分数重校准（BQSR）是其中开销最大的步骤之一，用于纠正系统性测序误差。尽管已有大量工作加速变异检测流水线的其他环节，针对 GPU 上的 BQSR 仍缺乏系统研究。 本文分析 BQSR 的计算与 I/O 瓶颈，并表明仅将关键阶段卸载到加速器不足以提升整体性能。随后，我们提出 X-BQSR，对包括 I/O、压缩和内核执行在内的整条 BQSR 流水线进行整体重设计，以更充分地利用 GPU 并行性。我们使用可移植的 SYCL 内核实现 X-BQSR，使其支持 NVIDIA、AMD 和 Intel GPU，同时实现原生 CUDA 和 HIP 后端用于对照，并与既有 FPGA 方案进行性能比较。评估结果显示，X-BQSR 相对标准 GATK 的加速比最高为 141.7 倍，相对一款专有 GPU 加速方案的加速比最高为 8.7 倍。

查看英文原文摘要

With the continued decline in sequencing costs, genomics-based precision medicine is gaining increasing importance. The Genome Analysis Toolkit (GATK) is the standard framework for converting raw genomic data into actionable variants, but one of its most expensive steps is base quality score recalibration (BQSR), which corrects systematic sequencing errors. Despite significant work on accelerating other parts of the variant calling pipeline, BQSR has not been systematically explored on GPUs. In this work, we analyze BQSR to identify computational and I/O bottlenecks and show that simply offloading key stages to an accelerator is insufficient to achieve overall gains. We then present X-BQSR, a holistic redesign of the entire BQSR pipeline, including I/O, compression, and kernel execution, to better leverage GPU parallelism. We implement X-BQSR using portable SYCL kernels for NVIDIA, AMD, and Intel GPUs, along with native CUDA and HIP backends for comparison, and we evaluate its performance against previous FPGA work. Our evaluation shows up to 141.7x acceleration compared to standard GATK and 8.7x acceleration compared to a proprietary GPU-accelerated solution.

核心结论
仅卸载 BQSR 的关键阶段不足以提升端到端性能。整体重设计流水线后，X-BQSR 相对标准 GATK 的加速比最高为 141.7 倍，相对一款专有 GPU 加速方案最高为 8.7 倍。
创新点
1. 分析 BQSR 的计算与 I/O 瓶颈，并评估仅卸载关键阶段对整体性能的影响；2. 提出 X-BQSR，整体重设计 I/O、压缩和内核执行以利用 GPU 并行性；3. 使用可移植的 SYCL 内核支持 NVIDIA、AMD 和 Intel GPU，并实现原生 CUDA 和 HIP 后端用于对照。

Measuring GPU Memory Traffic on the NVIDIA GB10 Without C2C Telemetry

arXiv 提交 2026-11-23 cs.AR cs.DC cs.PF 主题相关度 0.492

Deepak Panigrahy, Sirisha Kota, Aakash Tyagi, David Kebo 等 5 人

中文摘要

NVIDIA GB10 用于 DGX Spark 以及多家厂商的桌面 AI 系统，它通过 NVLink C2C 连接 Arm CPU 裸片和 Blackwell GPU 裸片。GPU 没有本地内存，因此所有未命中 GPU L2 缓存的访问都要经过 C2C，访问连接在 CPU 裸片上的 LPDDR5X 内存。然而，我们测试的系统所用软件并未提供用于统计这类流量的计数器。我们表明，由一个无需附加到目标工作负载的进程，通过 NVIDIA 的 CUPTI 采样接口每 10 ms 采样 5 个 GPU L2 扇区计数器，即可实时测量 GPU 内存流量，并区分拷贝引擎流量与 GPU 内核的读未命中及写入流量。对于大小已知的大规模流式传输，计数器测量值与已知传输量的偏差在 Acer GN100 上不超过 0.28%，在 DGX Spark 上不超过 0.005%。无论传输被拆分成多少次拷贝，计数器都能追踪实际传输量，并排除在 L2 中复用的数据。另一种容易想到的选择是 GPU 的 SMMU 计数器，它统计的是地址转换次数，无法提供字节数。将该方法应用于未经修改的服务器时，结果显示 Mistral 7B 在解码过程中每生成一个 token 读取 13.47 GiB，所读数据为该步用到的权重与键值（KV）缓存，读带宽达到 NVIDIA 标称内存带宽的 83%。我们将该方法作为开源工具发布。

查看英文原文摘要

The NVIDIA GB10, used in the DGX Spark and in desktop AI systems from several vendors, joins an Arm CPU die and a Blackwell GPU die with NVLink C2C. The GPU has no local memory, so every GPU access that misses in its L2 cache crosses C2C to the LPDDR5X attached to the CPU die. Yet the software on the systems we tested exposes no counter for this traffic. We show that five L2 sector counters of the GPU, sampled every 10 ms through NVIDIA's CUPTI sampling interface by a process that does not attach to the workload, measure GPU memory traffic live and separate copy engine traffic from the read misses and writes of GPU kernels. For large streaming transfers of known size, the counters agree within 0.28% on an Acer GN100 and within 0.005% on a DGX Spark, track the volume moved regardless of how it is split into copies, and exclude data reused in L2. The GPU's SMMU counter, a natural alternative, counts address translations rather than bytes. Applied to an unmodified server, the method shows Mistral 7B decode reading 13.47 GiB per token, the weights it uses plus its key value (KV) cache, at 83% of the memory bandwidth NVIDIA specifies. We release the method as an open source tool.

核心结论
通过 CUPTI 采样 GPU L2 扇区计数器，可以在缺少 C2C 流量遥测的 GB10 系统上实时测量 GPU 内存流量。对于大小已知的大规模流式传输，测量偏差在 Acer GN100 上不超过 0.28%，在 DGX Spark 上不超过 0.005%，且该方法测得 Mistral 7B 解码每个 token 读取 13.47 GiB，读带宽达到 NVIDIA 标称内存带宽的 83%。
创新点
1. 通过独立进程使用 CUPTI 每 10 ms 采样 5 个 GPU L2 扇区计数器，在无需附加到目标工作负载的情况下实时测量内存流量，区分拷贝引擎流量与 GPU 内核的读未命中及写入流量，并排除 L2 中复用的数据；2. 将该测量方法实现为开源工具。

ANOR: Scaling Sparse Attention with a GPU-PNM Computing Hierarchy

arXiv 提交 2026-11-23 cs.AR 主题相关度 0.472

Hyunsu Ye, Hyunmin Choi, Jaehong Cho, Jaeseo Lee 等 11 人

中文摘要

为长上下文大语言模型提供推理服务，需要保留每个请求的键值（KV）缓存，所需空间可能超过 GPU 显存容量。稀疏注意力在每个解码步只读取缓存中由当前查询决定的一小部分条目，但后续步骤可能选中其他条目，因此仍须保留完整缓存。通过 Compute Express Link（CXL）连接的近内存处理（PNM）设备可以容纳完整缓存，并在数据所在位置执行注意力计算。以往面向稀疏注意力的 GPU–PNM 系统以 PNM 为主，将大部分注意力计算交给 PNM。现有 CXL–PNM 设备的内存带宽远低于 GPU 的高带宽内存（HBM），因此这种执行方式会使 PNM 成为瓶颈，GPU 则因等待注意力结果而闲置。本文提出 ANOR，一个 GPU–PNM 联合加速系统。它利用稀疏注意力的选择局部性，由 GPU 利用缓存中近期被选中的条目完成大部分注意力计算，仅将缓存未命中的部分交给 PNM。由于 PNM 直接处理未命中，GPU 缓存更新可与当前解码步的执行解耦。我们设计了一种有界缓存更新策略，将更新量限制在后续解码步的命中率达到饱和所需的水平，以减少面向 GPU 的链路流量。我们还加入了一个小型片上提前流式缓冲区（Early Streaming Buffer，ESB），在 PNM 执行注意力计算时捕获 KV 数据，并将其以流式方式发往 GPU。即使 PNM 内存与面向 GPU 的链路带宽不匹配，这种方式也能避免大部分冗余 DRAM 读取。此外，我们提出自适应缓存因子机制，根据推理服务负载调整 GPU 缓存大小，平衡命中率和批大小。在涵盖 2 个模型和 3 种长上下文智能体工作负载的评估中，ANOR 的平均解码吞吐量分别达到 HiSparse 的 2.3 倍和 PNM 基线的 2.0 倍。结果表明，将 PNM 用作 GPU 内存层次结构中的计算层，比将其用作主要注意力计算引擎更有效。

查看英文原文摘要

Serving large language models with long contexts requires keeping the key-value (KV) cache of every request, which can exceed GPU memory capacity. Sparse attention reads only a small, query-dependent subset of this cache at each decoding step, yet must retain the full cache because later steps may select other entries. Processing-near-memory (PNM) devices attached through Compute Express Link (CXL) can hold the full cache and compute attention where it resides. Prior GPU-PNM systems for sparse attention are PNM-centric, processing most of the attention on the PNM. As existing CXL-PNM devices provide far less memory bandwidth than GPU HBM, this PNM-centric execution makes the PNM the bottleneck and leaves the GPU idle waiting for attention results. We present ANOR, a GPU-PNM joint acceleration system that exploits the selection locality of sparse attention by computing most of the attention on the GPU from a cache of recently selected entries and processing only the misses on the PNM. As the PNM processes cache misses directly, GPU cache updates can be decoupled from current-step execution. We develop a bounded cache-update policy that limits updates to the point where the hit ratio of later steps saturates, reducing GPU-facing link traffic. We add a small on-chip Early Streaming Buffer (ESB) that captures KV data during PNM attention and streams it to the GPU, avoiding most redundant DRAM reads despite the bandwidth mismatch between PNM memory and the GPU-facing link. We also propose an adaptive cache-factor mechanism that adjusts GPU cache size to the serving load, balancing hit ratio and batch size. Across two models and three long-context agentic workloads, ANOR improves decode throughput by 2.3x over HiSparse and 2.0x over a PNM baseline on average. These results show that PNM is most effective not as the primary attention engine but as a computing tier of the GPU memory hierarchy.

核心结论
在涵盖 2 个模型和 3 种长上下文智能体工作负载的评估中，由 GPU 执行大部分稀疏注意力计算、由 PNM 处理缓存未命中的 ANOR，平均解码吞吐量达到 HiSparse 的 2.3 倍和 PNM 基线的 2.0 倍。
创新点
1. 利用稀疏注意力的选择局部性，由 GPU 缓存近期选中的 KV 条目并完成大部分注意力计算，由 PNM 直接处理未命中，使 GPU 缓存更新与当前解码步解耦；2. 采用有界缓存更新策略，以后续步骤的命中率达到饱和所需的更新量为上限，减少面向 GPU 的链路流量；3. 引入片上 ESB，在 PNM 计算注意力时捕获 KV 数据并流式传给 GPU，减少冗余 DRAM 读取；4. 通过自适应缓存因子机制按服务负载调整 GPU 缓存大小，平衡命中率和批大小。

Generalized Tensor Parallelism: Powering Trillion-Parameter LLM Training at 10+ EFLOP/s

arXiv 提交 2026-11-24 cs.DC 主题相关度 0.456

Shiqing Fan, Deepak Narayanan, Jimmy Zhang, Jiangfei Duan 等 14 人

中文摘要
